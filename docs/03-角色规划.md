# 03 角色规划 —— 角色定义、授权矩阵与数据权限

> mse-mp 的角色与授权设计。权限点 id / code 见 [02-权限规划](02-权限规划.md)，功能点含义见 [01-功能规划](01-功能规划.md)。
> **重要：工程当前未随 jar 提供角色种子**（`db/mysql/` 两脚本只含业务表与基座注册，无 `sys_role` 种子）——本文角色为**建议角色**，供租户管理员在基座「角色管理」按需创建；如需种子化，见第五节落库建议。

## 一、角色模型说明

1. **全部为租户级角色**（`sys_role.tenant_id` = 当前租户）：mp 是租户端子应用（side=1），不涉及平台端角色；每个租户运营**自己的**公众号账号（`mp_account.tenant_id` 隔离），账号互不可见。
2. **租户超管不依赖角色**：`sys_user.super_admin=1` 的租户管理员天然拥有套餐域内全量权限码（6001-6011），本清单角色面向**业务岗位**分工。
3. **角色受套餐裁剪约束**：即使授予 mp_admin，其权限也以租户套餐勾选的 mp 菜单（431-436）为上界（见 [02-权限规划](02-权限规划.md) 第六节）。
4. **建议角色是分工起点不是终点**：租户管理员在基座「角色管理」按第四节矩阵勾选菜单与权限点即可复刻；一个员工可兼多角色，权限取并集。
5. **公众号管理员 ≠ 租户超管**：mp_admin 只管公众号业务域（账号接入/菜单/规则），不涉及用户、角色、系统管理等基座能力。

## 二、建议角色清单（3 个）

| 编码（建议） | 名称 | data_scope（建议） | 定位 |
| --- | --- | --- | --- |
| `mp_admin` | 公众号管理员 | 1 全部 | 账号接入与凭据、连通性、微信后台对接，全模块管理兜底 |
| `mp_content` | 内容运营 | 1 全部 | 自定义菜单策划与发布、自动回复规则与图文内容设计 |
| `mp_service` | 客服专员 | 1 全部 | 消息流水核查、粉丝档案查询、回复命中情况跟进 |

> data_scope 取「全部（1）」的依据：mp 业务数据没有部门/组织维度，数据边界就是**租户**（行级隔离由基座租户插件保证）与**账号**（页面按公众号下拉过滤），部门型 data_scope（本部门/仅本人）在 mp 无实际语义。若同一租户内需按号限权（如分号运营），一期无账号级权限模型，可通过「菜单 + 只读权限码」近似约束（客服只见粉丝/消息，不给账号管理码）。

## 三、角色 × 模块授权矩阵（建议）

图例：**●** 完整操作（查+写）　**▲** 只读　**—** 无权限

| 模块（menu_id） | 公众号管理员 mp_admin | 内容运营 mp_content | 客服专员 mp_service |
| --- | --- | --- | --- |
| 仪表盘（431） | ● | ▲ | ▲ |
| 公众号管理（432） | ● | — | — |
| 菜单配置（433） | ● | ● | — |
| 粉丝管理（434） | ● | ▲ | ●（页面只读） |
| 消息事件（435） | ● | ▲ | ●（页面只读） |
| 回复规则（436） | ● | ● | ▲ |

设计要点：

- **接入凭据收归管理员**：AppID/AppSecret/Token/EncodingAESKey 是公众号的"钥匙"，6001-6003（尤其 6002 编辑与凭据回显、测试）只给 mp_admin；内容运营与客服无需接触凭据。
- **内容运营双页签闭环**：菜单（6004/6005）与规则（6008/6009）构成「用户点菜单 → click 事件 → 菜单 Key 回复」的内容闭环，两页权限同授；Key 下拉在两页间联动，拆开授予会割裂操作。
- **客服全只读**：粉丝与消息页面本身只读（后端仅 `list` 码），客服再给 6008 规则查询——看流水时能对照「命中了哪条规则」；不给规则编辑（内容口径由内容运营统一维护）。
- **仪表盘随需**：管理员全量；运营与客服给 6011 只读便于看大盘与趋势，不授亦可。

## 五、种子落库情况与建议

1. **现状**：`V20261001_02_mp__mp_init.sql`（master 通道）只建 6 张 `mp_*` 业务表，**无 `sys_role` / `sys_role_menu` / `sys_role_permission` 种子**——新租户默认只有租户超管可用，业务角色需在基座「角色管理」按第三节矩阵手工创建。
2. **如需种子化（建议/规划）**：角色属租户库表，种子放 `mp-service/src/main/resources/db/mysql/` 新增版本文件（缺省 `-- mse-target: master`，命名 `V{yyyyMMdd}_{NN}_mp__roles.sql`），按 `code` 判重（`WHERE NOT EXISTS`）、绑定按 `(role_id, menu_id)` / `(role_id, permission_id)` 判重幂等插入；已应用脚本不再修改，调整授权一律新增版本文件。角色 id 建议从与权限段呼应的空号段取（登记 alloc-tables.md，与基座/其他工程核对后占用）。
3. **菜单与权限点不属本节**：属基座库全局表，已随 `V20261001_01_mp__mp_base.sql`（`-- mse-target: base`）由 starter-bridge 推送落库，见 [02-权限规划](02-权限规划.md)。
4. **与 mes 差异说明**：mse-mes 随 jar 提供 9 个角色种子（开箱即用）；mse-mp 一期选择「超管即用 + 建议角色文档化」的轻量路线——运营团队小（管理员+运营+客服常由 1-2 人兼任）时手工建角色成本更低，团队扩大后再种子化。

## 六、数据权限设计

| 场景 | 规则 | 依据 |
| --- | --- | --- |
| 跨租户 | 一律由基座租户插件行级隔离（`tenant_id`），与角色无关 | 多租户基线 |
| 账号维度 | 各页面「公众号」下拉仅列本租户账号；粉丝/消息/规则/菜单均挂 `account_id` 过滤 | 按号检索，非权限隔离 |
| 回调链路跨租户 | 唯一跨租户入口：按 AppID 全局定位账号（`runIgnore` 查号）后即 `runAs` 固定到其租户，粉丝/消息落库天然租户隔离 | AppID 全局唯一（回调路由要求） |
| 凭据可见性 | 凭据明文仅经 6001（`/mp/account/{id}/credentials` 接入配置弹窗）回显，该码只授 mp_admin | 密钥最小可见面 |
| 开放接口 | `open:mp:fans-page` / `open:mp:messages-page` 经 mse-open 凭证调用，租户经上下文隐式透传，与页面角色无关 | 能力开放接入标准 |
