# 05 配置手册（零基础版）—— 从零把微信公众号平台跑起来

> **这本手册是给谁的**：没接触过本系统、甚至没怎么接触过服务器软件的同事——实施工程师、现场 IT、接手部署的新人。你不需要看懂代码，照着做、每步核对「✅ 成功的标志」即可。
> 配套文档：跑起来之后怎么用，看 [04-操作说明书](04-操作说明书/README.md)；技术细节与架构，看工程 [README](../README.md) 与 [docs/01-功能规划](01-功能规划.md)。

## 一、先认识几个名词（2 分钟）

| 名词 | 是什么 | 打个比方 |
| --- | --- | --- |
| **Docker** | 容器软件，把 MySQL 等软件"打包"成一键安装 | 免安装的"绿色软件"运行器 |
| **MySQL** | 数据库，所有业务数据存在这里 | 大仓库的账本 |
| **Redis** | 缓存，存登录会话等临时数据 | 门卫的登记本 |
| **JDK 21** | Java 运行环境，后端 jar 包需要它 | 播放器（jar 是影碟） |
| **Maven** | Java 的打包工具，把源码编译成 jar | 印刷厂 |
| **Node.js** | 前端页面的构建运行环境 | 网页的发动机 |
| **Nacos** | 微服务模式下的"配置中心 + 通讯录" | 公司前台（单体模式用不到） |
| **单体 / 微服务** | 两种安装形态：单体=所有功能装在一个程序里；微服务=拆成多个程序各司其职 | 便利店 vs 购物中心 |
| **AppID / AppSecret** | 微信给每个公众号发的"账号 / 密钥"，接入的钥匙 | 门的钥匙（本系统加密保管） |
| **回调 URL** | 微信把用户消息送到你服务器的地址 | 收件地址（必须是公网能访问的） |
| **内网穿透** | 把公网域名映射到你本机电脑的工具（ngrok/nps 等） | 给没有公网地址的开发机装一个"门牌" |

> **新人建议选「单体」**：一个程序 + MySQL + Redis 就能跑全部功能（含公众号平台）。微服务是给有运维团队的正式生产环境用的（见第九节）。

## 二、你需要准备什么

| 项 | 要求 | 说明 |
| --- | --- | --- |
| 服务器/电脑 | 4 核 8G 起步，硬盘 ≥40G | Windows / Linux 均可 |
| 软件 | Docker（推荐）或：JDK 21 + MySQL 8 + Redis + Maven 3.9+ + Node.js 20+ | 路线 A 只需 Docker |
| 软件包 | 本仓库源码（git clone 或拿到压缩包） | jar 也可以直接找开发要成品 |
| **公网可达性** | 微信回调要求**公网 HTTPS 地址** | 生产用正式域名；开发联调用内网穿透（见第七节） |
| 公众号 | 至少一个可用于测试的公众号 + 管理员权限（看 AppID/AppSecret） | 未认证号也能接入，但无自定义菜单/粉丝资料等权限 |

## 三、路线 A：容器一键部署（推荐，约 30 分钟）

### 第 1 步：安装 Docker

- Windows：安装 Docker Desktop 并启动；Linux：安装 docker + docker compose 插件。
- ✅ 成功标志：命令行执行 `docker --version` 能输出版本号。

### 第 2 步：启动数据库和缓存

命令行进入仓库的 `mse-framework/docker` 目录，执行：

```bash
docker compose up -d mysql redis
```

- ✅ 成功标志：`docker ps` 里出现 `mse-mysql`、`mse-redis` 两个容器，状态 Up（首次要等 MySQL 初始化约 1 分钟）。
- 说明：这一步会创建 `mse_platform`（平台控制面 + 一期 mp 业务表所在业务库）等库，**不用你手工建表**。

### 第 3 步：启动应用（单体，含公众号平台全部功能）

单体形态 = 基座聚合工程引入 `mp-service` jar。仍在同一目录执行（首次会构建镜像，10~20 分钟属正常）：

```bash
docker compose --profile apps up -d --build mse-monolith
```

- ✅ 成功标志：浏览器打开 `http://localhost:8080` 能看到服务应答；`docker logs -f mse-monolith` 里出现 `Started ... in xx seconds`。
- mp 的 6 张业务表、菜单（430-436）与权限点（6001-6011）、子应用注册，都会**自动写入数据库**——业务表脚本随启动迁移、基座注册由推送通道自动应用，无需执行任何 SQL。

### 第 4 步：启动网页前端

```bash
cd mse-framework/mse-ui      # 基座门户（含公众号平台页面）
npm install
npm run dev
```

- ✅ 成功标志：浏览器打开 `http://localhost:3000` 看到登录页。

### 第 5 步：登录平台，开通租户

1. `http://localhost:3000` 用**平台超管**登录：账号 `platform`，密码 `admin123`（正式环境务必改密码）。
2. 「租户管理」→ 新建租户 → 按向导填写，系统自动生成该租户的管理员账号。
3. （可选）想要现成演示数据：执行 `mse-framework/docker/mysql/demo/` 下的演示脚本，得到示例租户。

### 第 6 步：给租户"点亮"微信公众号平台（关键！不勾菜单看不到系统）

用平台账号进「**套餐管理**」→ 编辑租户所用套餐 → 勾选「**微信公众号**」分组下的页面菜单（仪表盘 / 公众号管理 / 菜单配置 / 粉丝管理 / 消息事件 / 回复规则）→ 保存。

- ✅ 成功标志：用**租户管理员**重新登录后，左侧出现「微信公众号」菜单组。
- 原理：mp 的菜单默认是"封存"的，套餐勾选是租户可见的总开关。

### 第 7 步：建业务角色并验收

1. 系统**不预置**业务角色（与 MES 不同）——用租户管理员进「组织管理 → 角色管理」，按 [03-角色规划](03-角色规划.md) 第四节的勾选清单创建：`mp_admin` 公众号管理员、`mp_content` 内容运营、`mp_service` 客服专员（人员少时先只用超管+管理员两个角色也行）。
2. 验收主流程：按 [04-操作说明书](04-操作说明书/README.md) 走——接入公众号 → 微信后台服务器配置提交验证 → 「测试」通过 → 用微信发消息 → 消息事件页出现流水。走通即部署成功。

## 四、常用配置项速查

> 单体：配置文件 `mse-sample/mse-monolith/src/main/resources/application.yaml`（环境变量覆盖，不用改文件）。微服务：Nacos 的 `mse-mp.yaml`（见第九节）。

| 想改什么 | 环境变量 / 配置项 | 默认值 | 说明 |
| --- | --- | --- | --- |
| **凭据加密密钥** | `MSE_MP_CRYPT_KEY`（`mse.mp.crypt-key`） | `mse-mp-default-crypt-key-please-change` | **生产必须修改**！AppSecret/Token/AESKey/token 用它加密落库；**更换后历史密文无法解密，需重新录入凭据** |
| 微信 API 域名 | `MSE_MP_API_BASE`（`mse.mp.api-base`） | `https://api.weixin.qq.com` | 仅内网联调指向模拟器时才改 |
| 调微信超时 | `mse.mp.http-timeout-ms` | 3000（毫秒） | 回调处理须控制在微信 5 秒应答窗口内，一般不动 |
| 数据库地址/账号 | `MSE_MYSQL_HOST` / `MSE_MYSQL_PORT` / `MSE_MYSQL_USER` / `MSE_MYSQL_PASSWORD` | localhost / 3306 / root / 123456 | 用自己的 MySQL 时改 |
| 缓存地址 | `MSE_REDIS_HOST` / `MSE_REDIS_PORT` | localhost / 6379 | 登录会话依赖 Redis，必配 |
| 服务端口 | `server.port` | 单体 8080；微服务 mp-boot **8091** | |
| 前端代理目标 | `mp-ui/vite.config.ts` 里 target | `http://localhost:8080` | 微服务联调改网关 `http://localhost:48080` |

> 数据库建表、升级、种子数据全部**随启动自动执行**（版本化脚本，重复启动不会重复执行；失败会阻断启动——按日志修复后重启，不要跳过）。

## 五、前端（mp 子应用）的两种跑法

公众号平台页面不是独立网站，而是"挂"在基座门户里的子应用（微前端），子应用注册已随部署自动完成（name=mp）：

1. **开发调试**：`cd mse-modules/mse-mp/mp-ui && npm install && npm run dev`，启动在 `http://localhost:3500`；平台端「子应用管理」把 mp 的开发地址登记为 `//localhost:3500`，刷新门户即可嵌入使用。
2. **正式部署**：`npm run build`，产物按 `/sub-apps/mp/` 路径部署到静态服务器（构建已内置该前缀），子应用登记为生产地址 `/sub-apps/mp/`。

> 前提：第 6 步的套餐勾选已完成，否则页面登记了也看不见菜单。

## 六、Nacos 配置要点（微服务形态）

| 项 | 值 | 说明 |
| --- | --- | --- |
| 应用名 / 注册名 | `mse-mp` | spring.application.name，网关按它负载均衡 |
| 服务专属 Data ID | `mse-mp.yaml` | 端口 8091、`mse.mp.crypt-key` 等都在这里；本地留档 `mse-modules/mse-mp/docker/nacos/config/mse-mp.yaml` |
| 导入命令 | `CONFIG_DIR="$PWD/mse-modules/mse-mp/docker/nacos/config" sh mse-framework/docker/nacos/init-configs.sh` | 首次部署执行，把 mse-mp.yaml 写入 Nacos |
| 共享配置 | `mse-micro-common.yaml` / `mse-micro-db-biz.yaml` / `mse-micro-dubbo.yaml` | 数据源/Redis/Sa-Token/Dubbo 等基座统一管理，mp 工程不重复配 |
| 网关路由 | `Path=/mp/** → lb://mse-mp`（`mse-gateway.yaml` 已登记） | 白名单已含 `/mp/callback/**`（微信回调无登录态，以下游签名验签）；调整白名单须全量列出既有条目 |
| 可观测端点 | health / info / metrics / slowsql | actuator 已按此暴露 |
| Seata | 默认关停（`seata: false`） | mp 一期无跨库全局事务需求；启用全局事务再开 |

## 七、对接微信公众平台（部署后的核心动作，必做）

> 系统侧操作由公众号管理员在页面完成（分步截图级说明见 [04-操作说明书/01-公众号管理员](04-操作说明书/01-公众号管理员.md)），实施人员要保障的是**网络与配置一致性**。

1. **公网要求**：微信服务器要能访问你的回调地址 `https://<你的域名>/api/mp/callback/<AppID>`——生产环境用正式域名 + HTTPS 证书；**开发/内网环境没有公网地址时，用内网穿透**（ngrok/nps 等）把公网 HTTPS 域名映射到本机服务（单体映射到 8080，微服务映射到网关 48080 或 mp-boot 8091）。
2. **接入顺序**：先在系统「公众号管理 → 接入公众号」录入 AppID/AppSecret/Token/EncodingAESKey（与公众平台「设置与开发-基本配置-服务器配置」取值一致），再从「接入配置」弹窗复制回调 URL/Token/AESKey 回填公众平台并提交验证——**顺序颠倒验证必失败**（验证请求到达时系统还没有该号 Token）。
3. **两端一致性**：公众平台「消息加解密方式」（明文/兼容/安全）必须与系统录入的「消息加密方式」一致。
4. **验证链路**：公众平台提交验证（GET echostr）通过 → 「测试」按钮实取 access_token 通过 → 用微信发一条消息，「消息事件」页出现流水。

## 八、把粉丝/消息开放给第三方（可选）

本工程已把粉丝/消息只读查询自注册到开放平台 mse-open（`/open/api/mp/fans`、`/open/api/mp/messages`），无需任何 SQL 种子：

1. 部署 mse-open 工程；应用就绪后两个开放能力会自动出现在 mse-open「API 目录」（code：`open:mp:fans-page` / `open:mp:messages-page`），可启停。
2. 在 mse-open 创建第三方应用并授权上述能力，把凭证发给对接方即可；租户归属经调用上下文隐式透传。

## 九、微服务形态（进阶，多服务正式环境）

> 什么时候需要：用户量大、需要独立扩缩容、有多团队维护。门外汉/试点环境用第三节的单体即可。

1. 启动 Nacos（compose 已含）：`docker compose up -d nacos`，控制台 `http://localhost:18080`。
2. 把服务专属配置写入 Nacos（见第六节导入命令）。
3. 构建并启动：框架区 `mvn install -DskipTests` → 本工程 `cd mse-modules/mse-mp && mvn install -DskipTests` → `java -jar mp-boot/target/mp-boot-1.0.0-SNAPSHOT.jar`（端口 8091，注册进 Nacos；启动即自动建表 + 推送基座注册）。
4. 网关：确认 `mse-gateway.yaml` 里有 `/mp/** → lb://mse-mp`；基座前端开发代理用 `MSE_API_TARGET=http://localhost:48080 npm run dev`（网关）。
5. 可选开关：RocketMQ（`mq-starter` + name-server 地址）、独立库租户（平台端「租户数据源」界面维护，免重启）、信创数据库（启动参数 `--spring.profiles.active=dm` 或 `kingbase`——注意 mp 的达梦/金仓建表脚本一期未随 jar 提供，切换前先与开发确认）。

## 十、常见问题排查（按现象查）

| 现象 | 先检查什么 |
| --- | --- |
| 应用启动失败，日志报数据库连接错误 | MySQL 没起/地址密码错/账号无建库权限——`docker ps` 看容器，改环境变量后重启 |
| 日志报 Redis 连接错误 | Redis 没起或地址不对（登录会话依赖 Redis，必配） |
| 8080（或 8091）端口被占用 | 改 `server.port` 或停掉占用程序（Windows：`netstat -ano | findstr 8080`） |
| 登录后左侧没有「微信公众号」菜单 | 套餐没勾选 mp 菜单（见第 6 步），或该用户角色没授权菜单 |
| 登录后看得到菜单但页面空白/404 | mp 子应用没登记或地址不对（见第五节）；前端代理 target 指错了后端 |
| 接入公众号时提示 AppID 已存在 | AppID 全局唯一：该号已被（可能是其他租户）接入过，先确认归属 |
| 公众平台服务器配置「提交验证」失败 | ① 系统里还没录入该号（先接入再验证）；② 回调 URL 不对（用「接入配置」弹窗原样复制的）；③ 公网不可达（内网穿透没通）——公网访问 `https://<域名>/api/mp/callback/test` 有响应才说明入口通 |
| 「测试」按钮报 40125 | AppSecret 错误：公众平台重置后重新录入 |
| 「测试」或同步菜单报 48001 | 公众号未认证，无该接口权限：先微信认证 |
| 微信发消息，「消息事件」页没有流水 | ① 账号被停用；② 公众平台服务器配置未启用或被改过；③ 加密方式两端不一致；④ Token 状态列显示失败（按错误码处理） |
| 服务重启后凭据读不出来/测试全失败 | `mse.mp.crypt-key` 被更换过：历史密文无法解密，重新录入各号凭据（这就是生产部署前必须定好密钥的原因） |
| 接口报 404（微服务） | mp-boot 没注册到 Nacos，或网关路由没配 `/mp/**` |
| 界面/数据库中文乱码 | 建库与连接必须 utf8mb4（脚本已内置；自建库时确认字符集） |
| 启动日志报"脚本执行失败"并退出 | 数据库迁移是启动强校验：按日志提示修复后重启，不要跳过 |

## 十一、上线前检查清单

- [ ] **`mse.mp.crypt-key` 已改为随机强密钥**（默认值 `mse-mp-default-crypt-key-please-change` 绝不能带上生产），并妥善保管——换钥需重录全部凭据
- [ ] 修改所有默认密码（platform/admin123、数据库 root、Redis 密码）
- [ ] 数据库开启每日备份（mysqldump 或云快照）
- [ ] 回调地址为正式 HTTPS 域名（非内网穿透），证书有效
- [ ] 微信公众平台服务器配置已启用、Token/AESKey/加密方式与系统一致
- [ ] 前端走 HTTPS 与正式域名；mp 子应用登记改为生产地址 `/sub-apps/mp/`
- [ ] 微服务形态：Nacos 开鉴权、网关白名单按需最小化（`/mp/callback/**` 必须保留）
- [ ] 租户/套餐/角色初始化完成（第 6、7 步），用「公众号管理员」视角跑通接入→验证→收消息闭环
- [ ] 记录本次部署的版本号、日期与 crypt-key 的保管位置（密钥本身不入文档），便于后续升级追查
